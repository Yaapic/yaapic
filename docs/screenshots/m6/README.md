# M6 WinUI screenshots and visual review

Captures of the Milestone 6 WinUI views (Runner, Load test, Mock servers and Monitors, the folder context menu, the status bar items and
the rail), dark and light, taken from the Native AOT build (`dotnet publish -c Release -r win-x64 -p:PublishAot=true`). Since ADR 0023 the
automation tools are **views of the main window** (reached from the rail, the folder context menu, the palette or the status bar), so every
capture is the main window at 1440 x 900 px; there are no tool windows any more. The capture machine runs at 150 % display scale (the
window is about 960 x 600 dip). There is **no mockup for any milestone 6 screen**, so each screen is only related to the closest component
sheet (listed below). Every value on screen is fake: a loopback stub (`127.0.0.1:5199`) and a Yaapic mock server (`127.0.0.1:3000`) provide
the responses, the data file is a three-row CSV generated by the script, and everything lives in a throw-away workspace that is deleted
afterwards.

## Regenerate

```powershell
dotnet publish src/Yaapic.App.WinUI -c Release -r win-x64 -p:PublishAot=true
pwsh tools/screenshots/Capture-M6.ps1                      # all 18 files; -Only <screen> for one screen
```

`Capture-M6.ps1` runs `Capture-WinUI.ps1` once per file in English on the `-Seed m6` fixture (a `Demo API` folder with a passing,
a failing and a script-skipped request, a `Health checks` folder, `users.csv`) and retries a capture up to three times (the folder
context menu sometimes does not open when another window takes the foreground). New capture steps: `front:<title>`,
`clickitem:<name>:<n>`, `setvalue:<edit>=<text>`, `pickcombo:<combo>=<item>`, `openpath:<file>`, `http:<url>`, `probe:<url>`,
`dump:`/`tops:` (debug), `{TEMP}` in a step and `-Seed m6`. A flow goes back to the folder tree with `invoke:Collections` (the rail entry);
a tool is shown with `invoke:RailRunner|RailLoadTest|RailMockServers|RailMonitors` (the status bar items are `RunnerStatus`, `MocksStatus`,
`MonitorsStatus`). Raw keyboard and mouse steps are sent only while the Yaapic window is the foreground window (otherwise the step fails).
The script ends by killing the app, so a running load test never meets the "Close Yaapic?" prompt.

## Defects found by the capture

Fixed by M6-61 (earlier captures):

- **Mock servers: "Create a mock server..." (and adding a route) closed the application** under Native AOT. The route *Method* combo box took
  an `IReadOnlyList<string>` as `ItemsSource`, the stowed XAML exception documented in `ListMap.Entries`. Fixed with `ListMap.Lines` and the
  selection applied in the code-behind (commit `7c45c8a`).
- **Monitors: the Folder and Environment combo boxes were empty** and *Save* stayed disabled: the bindings rebuild the choice lists, which
  cleared the selection and wrote `null` back to the view model. The selection is now applied and read in the code-behind. The *enabled*
  switch also used the system blue instead of the Yaapic accent (`efcc2d4`).
- **Tool windows were sized in physical pixels** (1100 x 720), so at 150 % scale the Mock servers editor column was 173 dip wide and clipped
  (port, *Save*, headers cut off). Sizes are now device-independent and kept inside the work area (`26ca548`).
- **Runner layout**: the request list collapsed to a sliver as soon as a data file was loaded; *Export JUnit XML* was off the right edge; result
  rows squeezed the request name to one character; the rows list got only half of the height even when nothing was selected (`26ca548`, `2a6eba1`).
- **Load test showed "Scripts were not run during this load test."** after any test of requests that have scripts, although ADR 0019
  decides that scripts run (the capture's `skipRequest()` visibly skipped a request). The note and its test expectation were removed (`2a6eba1`).
